# 말로 부르는 버스 — 기능 규칙서

## 1. 문서 목적

본 문서는 상담원 통화 보조 기능의 동작 기준을 정의한다.

프론트엔드, 백엔드, LLM 모듈이 동일한 기준으로 동작하도록 다음 내용을 정의한다.

- 통화 내용에서 예약 정보 추출 기준
- 예약 양식 자동 입력 기준
- 정류장 후보 추천 기준
- `확인 필요` 판정 기준
- 상담원 수정 및 확정 기준
- 예약 저장 기준
- 누락·모호·충돌·정정 발화 처리 기준

본 문서에서 필수 구현 범위와 추가 논의가 필요한 기능을 구분한다.

---

## 2. 이번 개발 필수 구현 범위

이번 개발에서 필수로 구현하는 핵심 흐름은 다음과 같다.

```text
통화 내용
→ 예약 정보 추출
→ 예약 양식 자동 채움
→ 정류장 후보 추천
→ 확인 필요 표시
→ 상담원 확인·수정
→ 상담원 최종 확정
→ 예약 데이터 저장
```

필수 구현 기능은 다음과 같다.

1. 통화 내용에서 출발·도착·날짜·시간·인원을 추출한다.
2. 추출한 정보를 상담원 화면의 예약 양식에 자동 입력한다.
3. 이용자가 말한 장소를 등록된 정류장 목록과 매칭한다.
4. 하나로 결정할 수 없는 정류장은 후보를 표시한다.
5. 누락되거나 모호한 정보에는 `확인 필요`를 표시한다.
6. 상담원이 후보를 선택하거나 값을 직접 수정할 수 있도록 한다.
7. 모든 필수 정보가 확인된 경우에만 상담원이 예약을 확정할 수 있도록 한다.
8. 상담원이 최종 확정한 예약 정보를 저장한다.

AI는 예약 정보를 자동으로 확정하지 않는다.

---

## 3. 기본 원칙

1. AI는 상담원의 예약 접수를 보조한다.
2. AI가 추출한 값은 최종값이 아니라 상담원을 위한 제안이다.
3. 정보가 없거나 하나로 결정할 수 없으면 임의로 추정하지 않는다.
4. 정류장은 등록된 정류장 목록 안에서만 선택한다.
5. 정류장 목록에 없는 장소를 AI가 임의로 정류장으로 생성하지 않는다.
6. 출발·도착·날짜·시간·인원은 각각 독립적으로 상태를 판정한다.
7. 이용자가 기존 정보를 명시적으로 정정하면 가장 최근의 명시적인 값을 우선한다.
8. 상담원이 직접 확인하여 수정한 값은 AI의 기존 추출값보다 우선한다.
9. 모든 필수 항목이 유효해야 예약을 확정할 수 있다.
10. 최종 예약 확정은 반드시 상담원이 수행한다.

## 4. 필드 상태

각 예약 필드는 독립적으로 `확인 완료` 또는 `확인 필요` 상태를 가진다.

### 4.1 확인 완료

값이 존재하고 하나의 의미로 결정되며 유효성 검사를 통과한 상태이다.

화면 표시:

`✓ 확인 완료`

### 4.2 확인 필요

상담원의 추가 확인이 필요한 상태이다.

화면 표시:

`⚠ 확인 필요`

확인 필요의 원인은 다음과 같이 구분한다.

| 유형 | 의미 | 예시 |
|---|---|---|
| 누락 | 필수 정보를 말하지 않음 | 인원을 말하지 않음 |
| 모호 | 하나의 값으로 결정할 수 없음 | `회관 앞`에 해당하는 정류장이 여러 개 |
| 충돌·비정상 | 값이 다른 정보와 충돌하거나 유효하지 않음 | 출발=도착, 인원 0명 |
| 정정 | 이용자가 기존 정보를 변경함 | `9시… 아니 10시요` |

정정된 값은 이전 값을 대체하고 다시 유효성을 검사한다.

## 5. 예약 항목 정의

### 5.1 출발 정류장

필수 여부: 필수

최종값은 등록된 정류장의 ID를 사용한다.

함께 유지할 수 있는 정보:

- 이용자가 실제 말한 표현
- 추천 후보 정류장 ID 목록
- 추가 확인 필요 여부

#### 확인 완료

- 정확한 정류장명이 하나의 정류장으로 매칭됨
- 등록된 별칭이 하나의 정류장으로 매칭됨
- 상담원이 이용자에게 확인한 후 정류장 하나를 선택함

#### 확인 필요

- 출발지를 말하지 않음
- 정류장 후보가 여러 개
- `회관 앞`, `읍내`, `시장 쪽`처럼 하나로 결정할 수 없는 표현
- 등록된 정류장 중 후보가 없음
- 출발 정류장과 도착 정류장이 동일함

후보가 없으면 AI가 새로운 정류장을 생성하지 않는다.

### 5.2 도착 정류장

필수 여부: 필수

출발 정류장과 동일한 매칭 규칙을 적용한다.

정확한 정류장명 또는 등록된 별칭이 하나의 정류장으로 매칭되면 `확인 완료`로 처리한다.

누락, 복수 후보, 넓은 장소 표현, 후보 없음은 `확인 필요`로 처리한다.

출발 정류장과 도착 정류장이 동일하면 예약을 확정하지 않고 상담원이 다시 확인한다.

### 5.3 날짜

필수 여부: 필수

저장 형식 기본안:

`YYYY-MM-DD`

예:

`2026-11-10`

상대 날짜는 접수일을 기준으로 실제 날짜로 변환한다.

| 이용자 표현 | 처리 |
|---|---|
| 오늘 | 접수일 |
| 내일 | 접수일 + 1일 |
| 모레 | 접수일 + 2일 |

화면에서는 원래 표현과 변환된 날짜를 함께 표시할 수 있다.

예:

`내일 (2026-11-10)`

#### 확인 필요

- 날짜를 말하지 않음
- `다음 주`, `며칠 뒤`처럼 하나의 날짜로 결정할 수 없음
- `월요일`처럼 기준에 따라 날짜가 달라질 가능성이 있음
- 과거 날짜로 해석됨
- 서로 다른 날짜가 등장하고 최종 의도를 결정할 수 없음

### 5.4 시간

필수 여부: 필수

저장 형식:

`HH:MM`

24시간제를 사용한다.

| 이용자 표현 | 저장값 |
|---|---|
| 오전 9시 | `09:00` |
| 오전 9시 반 | `09:30` |
| 오후 2시 | `14:00` |
| 오후 2시 30분 | `14:30` |

#### 확인 필요

- 시간을 말하지 않음
- `9시`처럼 오전·오후가 불명확함
- `아침 일찍`, `점심쯤`, `저녁쯤`처럼 정확한 시간을 결정할 수 없음
- `2시에서 3시 사이`처럼 범위로 말함
- 서로 다른 시간이 등장하고 최종 의도를 결정할 수 없음

AI가 오전·오후 또는 정확한 시간을 임의로 결정하지 않는다.

### 5.5 인원

필수 여부: 필수

저장 형식:

1 이상의 정수

| 이용자 표현 | 저장값 |
|---|---:|
| 한 명 | 1 |
| 혼자 | 1 |
| 저 혼자 | 1 |
| 둘이 | 2 |
| 두 명 | 2 |

#### 확인 필요

- 인원을 말하지 않음
- `우리 가족`, `몇 명 같이`처럼 정확한 인원을 알 수 없음
- 숫자를 하나로 판단할 수 없음
- 0명 또는 음수 등 유효하지 않은 값

인원을 말하지 않았다는 이유만으로 `1명`을 기본값으로 넣지 않는다.

## 6. 정류장 추천 규칙

정류장 추천은 팀이 준비한 정류장 데이터 안에서만 수행한다.

정류장 데이터 예시:

```json
{
"id": "S01",
"name": "방림리 마을회관",
"alias": [
"방림리 회관",
"회관",
"마을회관"
]
}
```

정류장 추천은 다음 원칙을 따른다.

1. 정확한 정류장명과 일치하면 해당 정류장을 사용한다.
2. 등록된 별칭이 하나의 정류장과 매칭되면 해당 정류장을 사용할 수 있다.
3. 둘 이상의 정류장이 후보가 되면 자동으로 첫 번째 후보를 선택하지 않는다.
4. 복수 후보는 상담원에게 보여주고 이용자에게 확인하도록 한다.
5. 후보가 없으면 `확인 필요`로 처리한다.
6. AI의 일반 지식만으로 새로운 정류장을 생성하지 않는다.
7. 상담원이 이용자에게 확인하여 선택한 정류장이 AI 추천보다 우선한다.

---

## 7. 대화 문맥 처리 규칙

### 7.1 모든 장소를 예약 정보로 사용하지 않는다

발화에 등장한 모든 장소를 출발·도착으로 간주하지 않는다.

예:

> 제가 지금 회관에 있는데 내일은 시장 앞에서 타서 보건소 갈 거예요.

처리:

- `회관` → 현재 위치이므로 예약 출발지로 사용하지 않음
- 출발 → 시장 앞
- 도착 → 보건소

예약하려는 이동과 직접 관련된 장소만 추출한다.

### 7.2 모든 숫자를 예약 정보로 사용하지 않는다

예:

> 제가 70살인데 내일 오전 9시에 혼자 갈게요.

처리:

- `70` → 인원으로 사용하지 않음
- 시간 → `09:00`
- 인원 → `1`

숫자가 등장한 문맥을 기준으로 날짜·시간·인원을 구분한다.

### 7.3 이용자의 정정

이용자가 명시적으로 이전 값을 수정하면 가장 최근의 명시적인 값을 사용한다.

예:

> 내일 9시에요. 아 아니다. 10시 반에 갈게요.

처리:

- 기존 `09:00` 폐기
- 최종 시간 `10:30`

예:

> 회관에서 타요. 아니, 시장 앞에서 탈게요.

처리:

- 기존 출발 후보 폐기
- `시장 앞`을 기준으로 다시 정류장 후보 검색

### 7.4 상담원의 확인 질문

상담원이 특정 값을 제시하고 이용자가 명확하게 동의하면 해당 값을 확인된 값으로 사용할 수 있다.

예:

> 상담원: 방림리 마을회관 말씀하시는 거죠?
> 이용자: 네.

→ 방림리 마을회관 `확인 완료`

반대로 이용자가 부정하면 기존 값을 폐기한다.

예:

> 상담원: 방림리 마을회관 맞으시죠?
> 이용자: 아니요, 계촌리 회관이요.

→ 기존 후보를 확정하지 않고 `계촌리 회관`을 기준으로 다시 매칭한다.

### 7.5 STT 오류

음성 인식 결과가 없거나 상담원이 실제 통화와 다르다고 판단하면 AI가 값을 임의로 보완하지 않는다.

상담원이 직접 입력하거나 수정한 값이 STT·LLM 추출 결과보다 우선한다.

## 9. 상담원 수정 규칙

AI가 자동 입력한 예약 정보는 상담원이 수정할 수 있다.

출발·도착은 등록된 정류장 후보 목록에서 선택하는 것을 기본으로 한다.

상담원이 이용자에게 직접 확인하여 값을 수정한 경우 수정된 값이 AI의 기존 값보다 우선한다.

수정했다고 해서 자동으로 `확인 완료`가 되는 것은 아니다. 수정값도 유효성 조건을 만족해야 한다.

예:

- 인원 `0명` → 확인 완료 불가
- 출발과 도착에 동일 정류장 선택 → 확인 완료 불가
- 과거 날짜 입력 → 확인 완료 불가

---

## 10. 확정 가능 조건

다음 필드는 모두 필수이다.

- 출발
- 도착
- 날짜
- 시간
- 인원

다음 조건 중 하나라도 해당하면 예약을 확정할 수 없다.

- 필수값 없음
- `확인 필요` 상태가 남아 있음
- 입력 형식 오류
- 유효성 검증 실패
- 출발과 도착이 동일함

모든 필수 필드가 유효하고 `확인 완료` 상태이면 상담원이 예약을 확정할 수 있다.

## 11. 필수 기능 처리 흐름

```text
통화 시작
↓
통화 내용 입력
↓
AI 예약 정보 추출
↓
예약 양식 자동 채움
↓
정류장 후보 추천
↓
필드별 확인 필요 판정
↓
상담원 확인·질문
↓
상담원 선택·수정
↓
유효성 재검사
↓
모든 필수 항목 확인 완료
↓
상담원 확정
↓
예약 데이터 저장
↓
확정 결과 화면
```

## 12. 예약 저장 기본안

확정 시점의 상담원이 최종 확인한 값을 저장한다.

AI의 최초 추출값보다 상담원이 수정·확정한 최종값을 우선한다.

기존 JSON 초안을 기준으로 한 예시는 다음과 같다.

```json
{
"id": 12,
"channel": "상담원 통화",
"status": "확정",
"from": {
"id": "S01",
"said": "회관 앞",
"candidates": ["S01", "S02"],
"needsCheck": false
},
"to": {
"id": "S03",
"said": "보건소",
"candidates": ["S03"],
"needsCheck": false
},
"date": "2026-11-10",
"time": "09:00",
"people": 1,
"assist": [],
"transcript": [
["user", "내일 아침 아홉 시에 회관 앞에서 보건소 가요"]
]
}
```

날짜는 `내일` 등의 상대 표현이 아니라 실제 날짜 `YYYY-MM-DD`로 저장하는 것을 기본안으로 한다.

이용자가 실제 말한 장소 표현은 `said`에 유지한다.

정류장의 최종값은 정류장 ID로 저장한다.

`needsCheck`는 아래와 같은 의미로 사용하는 것을 제안한다.

- `needsCheck: true` → 상담원의 추가 확인이 필요함
- `needsCheck: false` → 추가 확인이 필요하지 않음

`needsCheck`의 최종 필드명은 15장의 데이터 구조 논의에서 확정한다.

## 13. 대표 예외 상황

| 이용자 발화 또는 상황 | 처리 |
|---|---|
| `버스 예약하려고요.` | 모든 필수정보 확인 필요 |
| `내일 9시에 보건소 가요.` | 출발·인원 등 누락 필드 확인 |
| `회관에서 읍내 가요.` | 출발·도착 정류장 매칭 결과에 따라 확인 필요 |
| `큰 느티나무 앞에서 탈게요.` | 후보가 없으면 확인 필요, 정류장 임의 생성 금지 |
| `9시에요. 아, 10시 반으로 해주세요.` | 기존 `09:00` 폐기, `10:30`으로 재판정 |
| `지금 회관인데 내일 시장 앞에서 타요.` | 현재 위치 회관을 출발지로 사용하지 않음 |
| `제가 70살이고 혼자 가요.` | 70을 인원으로 사용하지 않고 인원=1 |
| 출발=도착 | 재확인 전까지 확정 불가 |
| `비 안 오면 내일 갈게요.` | 실제 예약 의사를 확인한 후 진행 |
| STT 인식 실패 | 값을 추정하지 않고 상담원이 직접 확인·입력 |

## 14. 논의가 필요한 사항 — 기능 범위

아래 기능은 처리 방식을 기획안으로 정의하였으나 이번 개발의 필수 구현 범위에는 포함하지 않는다.

실제 구현 여부는 팀 회의에서 개발 일정과 난이도를 고려하여 결정한다.

### 14.1 왕복 예약

#### 제안 동작

한 번의 예약 데이터는 한 방향 이동 1건으로 처리한다.

왕복 요청은 가는 편과 오는 편을 별도의 예약 2건으로 분리한다.

예:

> 내일 9시에 회관에서 보건소 갔다가 11시에 다시 회관으로 올게요.

예약 1:

- 회관 → 보건소
- `09:00`

예약 2:

- 보건소 → 회관
- `11:00`

오는 편의 날짜 또는 시간이 누락되면 임의로 추정하지 않고 상담원이 확인한다.

#### 논의 사항

- 이번 시제품에서 왕복 자동 분리를 구현할지
- 구현한다면 두 예약을 연결할 필요가 있는지

### 14.2 한 통화의 복수 예약

#### 제안 동작

서로 다른 이용자·시간·목적지의 이동은 각각 별도의 예약으로 분리한다.

예:

> 저는 9시에 보건소 가고 남편은 10시에 시장에 가요.

→ 예약 2건으로 분리한다.

두 예약의 출발지 등이 동일하다고 임의로 가정하지 않는다.

공통 정보가 발화에서 명확한 경우에만 여러 예약에 함께 적용한다.

#### 논의 사항

- 이번 시제품에서 한 통화의 복수 예약 추출을 구현할지
- 구현한다면 여러 예약을 한 화면에서 보여줄지, 한 건씩 순서대로 보여줄지

### 14.3 확정 후 예약 변경

#### 제안 동작

기존 예약을 불러온 뒤 변경된 값만 수정한다.

```text
변경 요청
→ 기존 예약 확인
→ 변경할 값 수정
→ 전체 필드 재검증
→ 상담원 재확정
→ 변경값 저장
```

변경하지 않은 기존 필드는 유지한다.

기존 예약을 특정할 수 없으면 AI가 임의로 하나를 선택하지 않는다.

#### 논의 사항

- 이번 시제품에서 기존 예약 변경 기능을 구현할지
- 구현한다면 기존 예약을 어떻게 검색·선택할지
- 변경 이력을 별도로 저장할지

### 14.4 기존 예약 취소

#### 제안 동작

예약 데이터를 삭제하지 않고 상태를 `취소`로 변경한다.

```text
취소 요청
→ 기존 예약 확인
→ 취소 대상 선택
→ 이용자에게 대상 재확인
→ 상담원 취소 확정
→ status = 취소
```

AI가 이용자의 발화만으로 예약을 자동 취소하지 않는다.

취소 대상이 여러 개이면 상담원이 정확한 예약을 확인한다.

#### 논의 사항

- 이번 시제품에서 취소 기능을 구현할지
- 취소된 예약을 목록에서 어떻게 표시할지
- 취소 시각을 저장할지

## 15. 논의가 필요한 사항 — 데이터 구조

아래 항목은 기능 동작을 위해 개발자 간 데이터 형식을 맞춰야 하는 사항이다.

### 15.1 `check`와 `needsCheck`

기존 JSON 초안에서는 다음과 같이 `check`를 사용하고 있다.

```json
{
"check": true
}
```

그러나 `check`라는 이름만으로는 `true`가 확인이 완료되었다는 의미인지, 추가 확인이 필요하다는 의미인지 명확하지 않다.

따라서 다음과 같이 이름을 `needsCheck`로 변경하는 것을 제안한다.

```json
{
"needsCheck": true
}
```

의미는 다음과 같이 통일한다.

| 값 | 의미 | 화면 동작 |
|---|---|---|
| `needsCheck: true` | 상담원의 추가 확인이 필요함 | `⚠ 확인 필요` 표시 |
| `needsCheck: false` | 추가 확인이 필요하지 않음 | `✓ 확인 완료` 표시 |

예를 들어 이용자가 `회관 앞`이라고 말했고 후보가 두 개인 경우:

```json
{
"said": "회관 앞",
"candidates": ["S01", "S02"],
"needsCheck": true
}
```

프론트엔드는 `needsCheck: true`를 확인하고 해당 필드에 `⚠ 확인 필요`를 표시한다.

상담원이 이용자에게 확인하여 `S01`을 선택하면:

```json
{
"id": "S01",
"said": "회관 앞",
"candidates": ["S01", "S02"],
"needsCheck": false
}
```

로 변경한다.

즉 `needsCheck`는 해당 필드에 상담원의 추가 확인이 필요한지를 프론트엔드·백엔드·LLM이 공통으로 판단하기 위한 상태값이다.

#### 논의 사항

- 기존 `check`를 그대로 사용할지
- 의미가 명확한 `needsCheck`로 변경할지
- 어떤 모듈에서 `needsCheck` 값을 최종 판정할지

#### 제안

`needsCheck`를 사용하고 다음 의미로 통일하는 것을 권장한다.

- `true` = 확인 필요
- `false` = 확인 완료

### 15.2 목적 필드

화면 설계에는 `목적` 항목이 있으나 기존 예약 JSON 초안에는 목적 필드가 없다.

이번 시제품이 신규 이동 예약만 처리한다면 화면에서 `이동수단 예약`으로 고정 표시하고 별도의 데이터 필드를 저장하지 않는 방식을 제안한다.

향후 예약·변경·취소 등 여러 업무 유형을 하나의 데이터 구조에서 구분해야 한다면 별도의 필드 추가를 검토한다.

#### 논의 사항

- 목적은 화면에 `이동수단 예약`으로 고정 표시할지
- JSON에도 `purpose` 등의 필드를 추가할지

### 15.3 날짜 변환 위치

`내일`, `모레` 등의 상대 날짜는 실제 날짜 `YYYY-MM-DD`로 저장하는 것을 제안한다.

다만 실제 날짜로 변환하는 역할을 어느 모듈이 담당할지는 개발자 간 합의가 필요하다.

#### 논의 사항

- LLM이 실제 날짜까지 변환하여 전달할지
- 백엔드가 상대 날짜를 받아 실제 날짜로 변환할지

### 15.4 왕복 구현 시 연결 ID

14.1 왕복 예약을 이번에 구현하기로 결정한 경우에만 검토한다.

왕복을 예약 2건으로 분리할 경우 두 예약이 같은 왕복 요청이라는 것을 표시하기 위해 다음과 같은 연결 ID를 사용할 수 있다.

```json
{
"roundTripGroupId": "RT001"
}
```

왕복 기능을 구현하지 않는 경우 해당 필드는 필요하지 않다.

### 15.5 복수 예약 구현 시 연결 ID

14.2 복수 예약을 이번에 구현하기로 결정한 경우에만 검토한다.

한 통화에서 여러 예약이 생성되는 경우 같은 요청에서 생성된 예약임을 표시하기 위해 다음과 같은 연결 ID를 사용할 수 있다.

```json
{
"requestGroupId": "REQ001"
}
```

복수 예약 기능을 구현하지 않는 경우 해당 필드는 필요하지 않다.

### 15.6 취소 구현 시 취소 시각

14.4 취소 기능을 이번에 구현하기로 결정한 경우에만 검토한다.

취소된 예약의 취소 시각을 기록하려면 다음과 같은 필드를 사용할 수 있다.

```json
{
"cancelledAt": "2026-11-10T14:30:00"
}
```

취소 기능을 구현하지 않는 경우 해당 필드는 필요하지 않다.

## 16. 개발자별 필수 적용 기준

### 프론트엔드

필수 구현 범위에서 다음 기능을 담당한다.

- 예약 양식 표시
- 자동 추출 결과 표시
- 필드별 `확인 완료` / `확인 필요` 표시
- 정류장 후보 표시 및 선택
- 상담원 직접 수정
- 유효성 오류 표시
- 확정 가능 여부 표시
- 상담원 확정
- 확정 결과 표시

### LLM

필수 구현 범위에서 다음 기능을 담당한다.

- 통화 내용에서 예약 정보 추출
- 예약 문맥과 무관한 장소·숫자 구분
- 이용자의 정정 발화 반영
- 누락 정보를 임의 생성하지 않음
- 등록된 정류장 데이터를 기준으로 후보 추천
- 복수 후보 및 모호한 표현 식별

### 백엔드

필수 구현 범위에서 다음 기능을 담당한다.

- 상담원이 최종 확정한 예약 저장
- 예약 ID 및 상태 관리
- 최종 정류장 ID 저장
- 프론트엔드·LLM과 합의된 예약 JSON 구조 사용

왕복·복수 예약·기존 예약 변경·취소와 이에 필요한 추가 데이터 필드는 14장과 15장의 팀 논의 결과에 따라 구현 여부를 결정한다.

## 17. 팀 회의 확인 순서

### 필수 구현을 위해 결정해야 하는 사항

1. `check`를 유지할지 `needsCheck`로 변경할지
2. `needsCheck`를 어떤 모듈에서 최종 판정할지
3. `이동수단 예약`을 화면 고정값으로 표시하고, 목적 필드를 JSON에도 저장할지
4. 상대 날짜를 LLM과 백엔드 중 어디에서 실제 날짜로 변환할지

### 이번 개발에 포함할지 결정해야 하는 기능

1. 왕복 예약 자동 분리
2. 한 통화의 복수 예약 처리
3. 확정 후 기존 예약 변경
4. 기존 예약 취소

### 위 기능을 구현하기로 한 경우에만 결정할 사항

1. 왕복 예약의 `roundTripGroupId`
2. 복수 예약의 `requestGroupId`
3. 취소 예약의 `cancelledAt`

AI가 예약을 자동 확정하지 않고 상담원이 최종 확정한다는 원칙은 기존 기획을 그대로 따른다.
